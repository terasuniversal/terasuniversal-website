# Database Schema Audit — TERAS UNIVERSAL

Forensic comparison of the two migration tracks in `supabase/migrations/`, the generated TypeScript types, the Supabase clients, and every table/column reference in server actions and admin modules — **cross-checked against the live, connected Supabase project** (`iagzkrzeuawaxvacqprk`, "TERAS Certificate Verification", Postgres 17.6, `ap-southeast-1`) via direct schema and migration-history inspection.

**This live-DB check reverses what static analysis alone suggests.** Reading the code, the numbered track (0001–0021) looks "primary" because most admin modules query its table/column names (`training_schedules`, `trainers`, `companies`, `certificate_number`, etc.). But the live database has **none of those objects**. Only the legacy + compatibility track is actually deployed. No files were modified to produce this report.

> **Re-verified 2026-08-06** against the same live project via `list_migrations`/`list_tables`: identical 14 applied migrations, identical 21 live tables, identical column shapes (`courses` still the only table with data — 125 rows; every other table still 0 rows). No drift since this report was first written — all findings below still hold.

## 2. Obsolete Schema

**The numbered migration track, `supabase/migrations/0001_extensions_and_enums.sql` through `0021_automation_centre.sql`, has never been applied to the connected project.** Zero evidence of it in `list_tables` or `list_migrations`. It is a complete, self-consistent, 27-table clean-room schema design — matching almost exactly the nested `work/teras-admin-cms/teras-admin-cms/` deliverable snapshot in this repo (which stops at migration `0011`) and the architecture described in `DELIVERABLE.md` — but it exists **only as files on disk**. Running it against the live database now would fail immediately: `CREATE TYPE user_role`/`content_status` and `CREATE TABLE public.profiles`/`public.courses` in `0001`–`0003` are not `IF NOT EXISTS`-guarded, and those types/tables already exist live with different (compatibility-track) definitions.

Also obsolete/dead-on-arrival even within the compatibility track itself: `cms_content` and `cms_media` (generic polymorphic tables from `production_cms_additive_compatibility`) are live but **empty and unused by any code path** — the dedicated `news_posts`/`faqs`/`downloads`/`gallery_images`/`media`/`media_folders` tables created three days later (per repo file `20260724120000_provision_admin_content_modules.sql`) superseded them, yet nothing dropped them.

## 5. Column Mismatches

All confirmed against the **live** column list (`list_tables`, verbose).

**`courses`** — live table carries columns from *three* generations simultaneously:
- Legacy/original: `course_code` (unique), `course_name`, `description`, `validity_months`, `active`
- Compatibility-track additions: `title`, `slug`, `category`, `summary`, `overview`, `duration`, `objectives`, `target_audience`, `requirements`, `modules`, `faq`, `hero_image_url`, `fee`, `featured`, `sort_order`, `deleted_at`, `created_by`, `updated_by`, `delivery_modes` (`text[]`), `seo_title`, `seo_description`, `published_at`
- **Two independent, live, parallel status columns**: `cms_status` (enum `content_status`: draft/published/archived) and `status` (`text`, its own CHECK constraint, same three values) — confirmed coexisting in the live schema exactly as flagged by static analysis. Nothing unifies them; `app/admin/(protected)/courses/actions.ts` writes only `status` (text), so `cms_status` is dead weight that silently drifts out of sync.

**`participants`** — live shape is **entirely the legacy one**: `id`, `participant_code` (not `participant_id`), `identity_no`, `identity_last4`, `email`, `phone`, `organization` (not `company` — though `company` also exists as a separate later-added column), `position`, `address`, `notes`, `status` (`text`, CHECK `active`/`inactive` only — two values, not a lifecycle enum), `schedule_id`, `deleted_at`, `created_by`, `updated_by`. **None** of the numbered track's 0012 columns exist: no `ic_passport_no`, `nationality`, `gender`, `date_of_birth`, `emergency_contact_name`, `emergency_contact_phone`, `registration_date`, `company_id`. `app/admin/(protected)/participants/actions.ts` writes `full_name`, `ic_passport_no`, `nationality`, `gender`, `date_of_birth`, `emergency_contact_name`, `emergency_contact_phone`, `registration_date`, `company_id`, `status` (expects `registered/confirmed/attended/no_show/cancelled`) — **every one of these except `schedule_id`/`full_name`/`phone`/`email`/`company` is a write to a column that does not exist**, and `status` values the code writes fail the live 2-value CHECK constraint outright.

**`certificates`** — live shape is the legacy one: `certificate_no` (not `certificate_number`), `participant_name`/`course_name` (denormalized snapshot text, not solely FK-derived), `training_start_date`/`training_end_date`, `issue_date`/`expiry_date` (these two happen to match the numbered track's post-0016 renamed names — coincidental overlap), `status` (`text`, CHECK `valid`/`expired`/`revoked` — 3 values, not the numbered track's 5-value `draft/pending/issued/revoked/expired/archived` enum), `trainer_name`, `venue`, `identity_no`, `identity_last4`, `instructor`, `certificate_file_url`, `public_verification_enabled`, `metadata` (jsonb). **Missing entirely**: `certificate_number`, `verification_code`, `verification_token`, `verification_url`, `template_id`, `issued_by`, `remarks`, `verification_enabled`, `pdf_path`, `qr_code_path`, `schedule_id`. `app/admin/(protected)/certificates/actions.ts` reads/writes `certificate_number`, `holder_name`, `issue_date`, `issued_by`, `verification_token`, `verification_url`, `expiry_date`, `remarks`, `verification_enabled`, `template_id`, `schedule_id` — **almost none of these columns exist live**; this module cannot function against the connected database as written.

**`attendance`** — live: `id`, `schedule_id` (→ `course_schedules`), `participant_id`, `session_date`, `present` (boolean), `remarks`, `recorded_by`, timestamps. **Missing**: `attendance_id`, `attendance_status` (enum), `check_in_time`/`check_out_time` (as `timestamptz` — the app writes these), `attendance_method`, `deleted_at`. `app/admin/(protected)/attendance/actions.ts` writes `attendance_status`, `check_in_time`, `check_out_time`, `deleted_at` — none exist live.

**`assessments`** — live: `id`, `schedule_id`, `participant_id`, `assessment_type` (plain `text`, no enum), `score`, `max_score` (default 100), `result` (`text` CHECK, 5 values matching the numbered track's `pending/competent/not_yet_competent/pass/fail`), `assessed_at`, `remarks`. **Missing**: `assessment_id`, `theory_score`, `practical_score`, `overall_score` (generated), `competency_status`, `assessment_date`, `assessor_id`, `locked`/`locked_at`/`locked_by`. `app/admin/(protected)/assessment/actions.ts` writes `theory_score`, `practical_score`, `competency_status`, `assessment_date`, `assessor_id`, `locked` — none exist live; only `result`/`remarks`/`schedule_id`/`participant_id` overlap.

## 6. Foreign Key Mismatches

- Live `participants.schedule_id` → **`course_schedules.id`**. Application code across `training_schedules`-referencing modules (schedules, attendance, assessment, dashboard, reports) assumes `schedule_id` points at a `training_schedules` row — that table doesn't exist, so any join/select expecting `training_schedules(...)` embedded resource syntax (PostgREST) fails outright.
- Live `certificates` has **no `schedule_id` column at all** — the numbered track's `certificates.schedule_id → training_schedules.id` FK is pure fiction against this database. `app/admin/(protected)/certificates/actions.ts` writing `schedule_id` into an insert/update payload will be rejected by PostgREST (unknown column).
- Live `certificates.course_id → courses.id` and `certificates.participant_id → participants.id` **do** exist and match what the app expects — these two FKs are safe.
- `attendance.schedule_id → course_schedules.id`, `assessments.schedule_id → course_schedules.id` (live) vs. the app's implicit assumption of `training_schedules.id` — same class of break as participants.
- No FK exists anywhere live from any table to a `trainers` or `companies` table, because neither table exists — `trainers.id`/`companies.id` as FK targets referenced throughout the Trainers/Companies/Schedules/Certificates modules are dangling assumptions, not real constraints.

## 7. RLS Differences

- **Enable vs. force**: the live/active track only ever runs `alter table ... enable row level security` — never `force row level security`. The numbered (unapplied) track forces RLS on every table. Practical effect on the live DB: the table owner role and any role with `BYPASSRLS` are *not* subject to RLS — a materially weaker posture than the numbered track's design, though not exploitable via the app's own service-role/anon/authenticated roles since none of those have `BYPASSRLS`.
- **Role-check mechanism**: live policies mix two generations — `admin_users`-membership `EXISTS` subqueries (original `certificates`/`participants`/`courses`/`certificate_import_logs` policies from `certificates.sql`/`certificate_import_logs.sql`) alongside newer `app.is_editor()`/`app.is_admin()` enum-role-based policies (everything created by `cms_compatibility_security` onward: `profiles`, `course_schedules`, `attendance`, `assessments`, `cms_content`, `cms_media`, `media*`, `downloads`, `news_*`, `gallery_*`, `faq_*`, `company_profile`). Both mechanisms are simultaneously live and independently enforced — a user only in `admin_users` but with no `profiles` row (or `role='editor'` default) has certificate/course/participant access but not CMS-content access, and vice versa.
- `role_policies.sql` (live, via `restrict_legacy_certificate_rpc`/`replace_broad_client_deny_with_role_policies`) added `anon`-restrictive `DENY` policies on `certificates`/`participants`/`courses` and revoked `anon`'s prior blanket `SELECT` grant on `certificates` — public certificate lookup is now channeled exclusively through the `SECURITY DEFINER` RPC `verify_certificate_by_value`, confirmed still directly callable by `anon`/`authenticated` per the live security advisor (flagged `WARN`, intentional-looking but worth confirming with the team it's meant to stay `SECURITY DEFINER` + anon-executable).
- **`media_folders` has no public/staff read policy at all** in the live-equivalent definition (`20260724120000`-style: only `media_folders_editor_all` using `app.is_editor()`), despite a `select` grant to `anon` — meaning RLS silently returns zero rows for any non-editor `SELECT`, including the public site if it ever tried to read folders (it doesn't today, but `app/admin/(protected)/media/page.tsx` requires `is_editor()` already, so this is latent rather than currently broken).
- The numbered (unapplied) track's RLS is entirely irrelevant to current production security — it cannot be evaluated against a database it was never applied to. Do not use it as a reference for "what policies currently protect this data."

## 8. Migration Conflicts

- **Repo files don't match live migration history byte-for-byte.** The repo's `supabase/migrations/20260721030247_cms_compatibility_security.sql` differs in timestamp from the live-applied `20260721030423 cms_compatibility_security` (03:02:47 vs 03:04:23) — same for `move_citext_out_of_public` (030507 vs 030532), `production_cms_additive_compatibility` (030829 vs 030958), `add_course_delivery_modes` (054100 vs 054131), `add_course_status_compatibility` (054355 vs 054342, note the order is even swapped relative to filename sort). These are almost certainly the same logical changes re-exported/renamed locally after being applied via the Supabase dashboard or CLI, but it means **the repo cannot be treated as an authoritative diff source against the live project** — filenames alone don't prove content identity, and `supabase db push` using these files against this project would likely re-run (or conflict trying to re-run) already-applied DDL.
- **A live migration has no corresponding file in the repo at all**: `20260805024446 fix_courses_cms_fields` (applied one day before this audit, 2026-08-06). Its content is unknown from the repo alone — this is a real gap between what's deployed and what's version-controlled.
- **A repo file has no corresponding entry in live migration history**: `20260724120000_provision_admin_content_modules.sql` never appears in `list_migrations`, yet every table it defines (`media`, `media_folders`, `downloads`, `news_categories`, `news_posts`, `gallery_categories`, `gallery_images`, `faq_categories`, `faqs`, `company_profile`) exists live. Most likely explanation: it was applied out-of-band (SQL editor, not tracked as a numbered migration) or folded into a differently-named migration not reflected by the repo's filename. Either way, migration history and repo contents have drifted apart in both directions.
- **The two schema tracks were never meant to run in the same database**, but the live database is proof they partially did anyway (`profiles`, `course_schedules`, `attendance`, `assessments`, `cms_content`/`cms_media` all came from the compatibility track's own fresh `CREATE TABLE`s — not from the numbered track). If anyone ever runs `0001_extensions_and_enums.sql` onward against this project now, expect immediate failure at `0002_core_auth_rbac.sql`'s `create table public.profiles` (already exists, different shape) or `0001`'s `create type user_role` (already exists) — none of the numbered track's DDL uses `IF NOT EXISTS`/guarded blocks the way the compatibility track consistently does.
- **Internal duplication within the live/active track itself**: `cms_content`/`cms_media` (generic, empty, unused) vs. `news_posts`/`faqs`/`downloads`/`gallery_images`/`media`/`media_folders` (dedicated, actually used) — both live simultaneously from migrations three days apart, nothing reconciles them.
- `pg_trgm` extension confirmed still live in `public` schema (security advisor `WARN`) — the `move_citext_out_of_public` migration relocated `citext` but the very next migration (`production_cms_additive_compatibility`) reinstalled `pg_trgm` straight back into `public` with no schema qualifier, undermining the hardening the prior migration just did.

## 9. Which Schema the Application Code Actually Uses

**Split down the middle, and the split determines what's functional vs. broken in production right now:**

**Aligned with the live database (functional or close to it):**
- `app/admin/(protected)/courses/**`, `lib/public-content.ts`'s course reads — the live `courses` table has `title`/`slug`/`status`/`featured`/`sort_order`/`delivery_modes`/`seo_*` etc. from the compatibility-track additions, which is what these files write/read. Likely functional, modulo the dual `status`/`cms_status` column oddity.
- News, Gallery, FAQ, Downloads, Company Profile, Media modules (`app/admin/(protected)/{news,gallery,faq,downloads,company,media}/**`) — live tables `news_posts`/`news_categories`/`gallery_images`/`gallery_categories`/`faqs`/`faq_categories`/`downloads`/`company_profile`/`media`/`media_folders` match the compatibility track's `20260724120000`-equivalent shape, which is what these action files target.
- `app/api/admin/login/route.js` (the route flagged as "orphaned" by static analysis) — actually the **only** login path that matches the live `admin_users` table. It's not necessarily dead code; it may be a deliberate fallback or a leftover primary path — worth confirming with whoever owns auth which one is meant to be live, since the login *page* calls the other (`profiles`-based) path via a server action.
- `app/api/admin/certificates/route.js` — matches the live `certificates`/`courses`/`participants` legacy column names (`certificate_no`, `course_name`, `identity_no`, `participant_name`) almost exactly. This is the module that's actually schema-correct, despite looking like the odd one out next to the rest of `app/admin/(protected)/certificates/**`.

**Misaligned with the live database (will fail at runtime with PostgREST "relation/column does not exist" errors):**
- `app/admin/(protected)/schedules/**`, `attendance/**`, `assessment/**`, `trainers/**`, `companies/**`, `certificates/**` (the main admin CRUD path, not the API route), `certificates/templates/**`, `automation/**`, `reports/**`, `audit/**`, `users/**`, `dashboard/page.tsx` (queries `training_schedules`/`certificates`/`assessments` with mismatched columns) — these query `training_schedules`, `schedule_participants`, `trainers`, `companies`, `certificate_templates`, `certificate_verifications`, `automation_runs`, `automation_templates`, `audit_logs`, and the `v_*` reporting views, **none of which exist**, or write columns (`ic_passport_no`, `certificate_number`, `attendance_status`, `theory_score`, etc.) that don't exist on the live tables they do share a name with.
- `lib/public-content.ts`'s `getUpcomingSchedules()` queries a table literally named `schedules` — which exists in **neither** live schema nor the compatibility track (only in the numbered track's `0003`, also unapplied). The public training-calendar section of the website is reading from a table that doesn't exist at all.

**Net assessment:** the content-management half of the admin CMS (Courses, News, Gallery, FAQ, Downloads, Company, Media) is schema-correct and should work. The operations half (Schedules, Trainers, Companies, Attendance, Assessment, the full Certificates engine, Automation, Reports, Audit, Users) — which is most of what `DELIVERABLE.md` and the module docs (`TRAINING_SCHEDULE.md`, `TRAINER_MANAGEMENT.md`, `CERTIFICATE_ENGINE.md`, etc.) describe as built and production-ready — is built against a schema that was designed but never migrated in, and will not function against the connected Supabase project as currently deployed. `lib/supabase/database.types.ts`'s hand-curated types only cover `profiles`/`courses`/`enquiries`/`proposal_requests` and fall back to `any` for everything else (and `server.ts` casts its client to `any` regardless), so **TypeScript provides zero protection against any of this** — `tsc --noEmit` passes cleanly even though the majority of admin queries would fail at runtime.

## 10. Safe Migration Strategy

1. **Capture live truth into the repo before doing anything else.** Run (or use the Supabase MCP tools already available) to pull the exact current schema and reconcile it against `supabase/migrations/`. In particular, recover the content of `20260805024446_fix_courses_cms_fields` (applied live, no matching repo file) and confirm whether `20260724120000_provision_admin_content_modules.sql` in the repo is byte-identical to whatever actually ran. Do this with `mcp__claude_ai_Supabase__list_migrations` / a schema diff, not by guessing from filenames.
2. **Do not run `0001_extensions_and_enums.sql` onward against this project.** It is not idempotent against the live schema and will fail on the first conflicting `CREATE TYPE`/`CREATE TABLE`. Treat the numbered track as a design reference only, not an executable migration path, until it's rewritten additively (guarded `IF NOT EXISTS`/`DO` blocks, like the compatibility track already does) against the live starting point.
3. **Make an explicit product decision, then execute it as one direction, not a merge of both:**
   - **Option A — adopt the live/legacy schema as canonical.** Rewrite the operations-side admin modules (Schedules, Trainers, Companies, Attendance, Assessment, Certificates, Automation, Reports, Audit, Users) to target `course_schedules`/the legacy `participants`/`certificates` column names instead of `training_schedules`/`ic_passport_no`/`certificate_number`/etc. This is less migration risk (no data movement, `courses`' 125 live rows untouched) but a large application-code rewrite, and it means abandoning much of the richer numbered-track design (attendance status enum, locked assessments, certificate templates, audit log, reporting views) or re-adding those pieces additively on top of the live schema.
   - **Option B — migrate the live database forward to the numbered-track shape.** Write new, guarded (`IF NOT EXISTS`/backfill-safe) migrations that: add the missing columns to `participants`/`certificates`/`attendance`/`assessments` (mirroring what `0012`/`0016`/`0014`/`0015` intend) rather than dropping and recreating those tables; create the missing tables (`training_schedules` + backfill from `course_schedules`, `trainers`, `companies`, `certificate_templates`, `automation_*`, `audit_logs`, `venues`); and reconcile `courses.status`/`cms_status` into one column. This preserves the already-written operations UI code but requires careful, tested data migration (especially `course_schedules` → `training_schedules` and any way to reconstruct `trainer`/`company` associations that don't exist as FKs today).
   - Either way, **use `mcp__claude_ai_Supabase__create_branch`** to test the consolidation migration(s) against a branch database before touching production, especially given `courses` already holds real content.
4. **After landing on one schema, regenerate `lib/supabase/database.types.ts`** via `mcp__claude_ai_Supabase__generate_typescript_types` (or the Supabase CLI equivalent already documented in `README.md`), and **remove the `as any` casts in `lib/supabase/server.ts`** so TypeScript actually enforces table/column correctness going forward — this entire audit exists because that safety net was disabled.
5. **Resolve the two divergent auth/certificate code paths deliberately, not by omission**: decide whether `app/api/admin/login/route.js` (`admin_users`) and `app/api/admin/certificates/route.js` (legacy certificate columns) are the intended production path or dead code to delete — right now they're the *only* parts of the app that are unambiguously schema-correct, which is a strong signal they may still be load-bearing rather than orphaned.
6. **Reconcile RLS to one model** (`admin_users` membership vs. `profiles.role` hierarchy) rather than leaving both live simultaneously — decide which is authoritative and drop policies/helper functions for the other to avoid a user having inconsistent access across table groups.
7. Once the schema is settled, delete or clearly relabel whichever of the two migration tracks in `supabase/migrations/` is not the chosen path (e.g. move the numbered track to a `docs/schema-design-reference/` folder with a README noting it was never applied) so future contributors — human or AI — don't repeat this audit from scratch assuming file presence equals deployment.
