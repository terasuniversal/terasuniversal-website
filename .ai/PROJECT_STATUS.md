## Claude Code correction — 2026-08-28 (is_test column ORDER: my inference was wrong, fixed with drop+create)

**Trigger**: the human ran the exact live check my previous entry asked for — a direct ordinal-position query against production's `information_schema.columns` for `public.v_sales_lead_inbox` via Supabase MCP (ref `iagzkrzeuawaxvacqprk`) — and it disproved my inference.

**What I got wrong**: I had reasoned that because `create or replace view` can only *append* new trailing columns (never reorder or insert among existing ones), `is_test` must be the *last* column in production's live view, since that's the only way an ad hoc addition could have landed there. That reasoning about the Postgres constraint was correct; the conclusion from it was not, because I was reasoning about how a *fresh addition via `create or replace view`* would have to land — but nothing establishes that whatever untracked process modified production's view actually went through that exact path, and it evidently didn't.

**Confirmed live column order for `public.v_sales_lead_inbox` on production**:
```
1 lead_metadata_id   6 follow_up_at   11 created_at    16 phone
2 lead_source        7 priority       12 updated_at    17 subject
3 source_id          8 lost_reason    13 contact_name
4 status             9 won_at         14 company
5 assigned_to       10 is_test        15 email
```
`is_test` sits at position 10, between `won_at` and `created_at` — not trailing. This makes the fix from the previous entry (appending `m.is_test` after `subject` in a `create or replace view`) **also wrong** and would have failed on production with `cannot drop columns from view` (because reproducing production's real order requires `is_test` mid-list, which a plain append can't do) while simultaneously being unsafe on staging (inserting `is_test` in the middle of staging's current — is_test-less — 16-column view would count as reordering staging's own existing columns, equally forbidden).

**Fix applied to `supabase/migrations/20260828120000_promote_marketing_contact_to_sales.sql`** (file only — nothing applied to any database):
1. Replaced `create or replace view public.v_sales_lead_inbox ...` with `drop view if exists public.v_sales_lead_inbox;` followed by `create view public.v_sales_lead_inbox ...`. Dropping first removes the "must reproduce existing column order" constraint entirely, so one statement can define the single canonical order and apply cleanly regardless of an environment's starting shape (production's drifted 17-column view, staging's original 16-column view, or no view at all on a fresh environment).
2. Moved `m.is_test` in the `select` list to sit between `m.won_at` and `m.created_at`, matching production's confirmed live order exactly.
3. Checked for hard dependencies before relying on a plain (non-`CASCADE`) `drop view`: grepped every tracked migration referencing `v_sales_lead_inbox` (`20260814120000` — the original `create`; `20260814150000`, `20260814165048`, `20260814270000` — all `app.convert_lead_to_opportunity`-family functions). None of them build a view/materialized view on top of it; they all reference it as a plain `select ... into v_lead from public.v_sales_lead_inbox` inside a PL/pgSQL body, which is a runtime name lookup, not a catalog-level (`pg_depend`) dependency — it cannot block `drop view` and keeps working unchanged afterward since it uses `select *` and every column name is preserved. Documented in the file that this doesn't rule out an *undocumented* dependency from the same untracked drift, and that a `pg_depend` check against production is a reasonable final step before applying if extra certainty is wanted.
4. Documented that because `drop view` + `create view` (unlike `create or replace view`) does **not** preserve existing grants, the `revoke`/`grant` statements already present after the view definition are no longer optional belt-and-suspenders redundancy — they are now the only thing restoring the view's access grants, and must stay in the file.
5. Rewrote both the "is_test" comment block and the top-of-file "Ordering / dependency" note to state the now-confirmed real column order instead of the earlier inference, and to explicitly record that the earlier trailing-column assumption was checked and found wrong (not silently replaced).

No other SQL changed: the RPC body (`promote_marketing_contact_to_sales`), the CASE-widening logic for `marketing_contact`, and `20260828110000_reconcile_sales_is_test_classification.sql` (columns/indexes/triggers/`mark_lead_test`) are unchanged from the previous entry.

## Claude Code fix — 2026-08-28 (v_sales_lead_inbox grants after drop+create were incomplete)

**Trigger**: the human directly queried production's actual grants on `public.v_sales_lead_inbox` (ref `iagzkrzeuawaxvacqprk`) and confirmed:
- `anon` — no privileges at all
- `authenticated` — SELECT only
- `service_role` — SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
- `postgres` — SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER

**Gap found**: the previous entry's fix (switching to `drop view if exists` + `create view`) correctly flagged that DROP VIEW wipes existing grants and that the revoke/grant block afterward is no longer optional — but the block that was actually in the file only handled `anon` (revoke all) and `authenticated` (grant select, revoke the rest). It had no statement at all for `service_role` or `postgres`, so after a `drop view` + `create view`, those two roles' full access would not have come back unless Supabase's ambient default-privilege/ownership behavior happened to restore it — an assumption that was not verified, in the same spirit as the column-order assumption that already turned out wrong once in this file.

**Fix applied to `supabase/migrations/20260828120000_promote_marketing_contact_to_sales.sql`** (file only — nothing applied to any database):
1. Added two explicit grant statements after the existing anon/authenticated lines:
   `grant select, insert, update, delete, truncate, references, trigger on public.v_sales_lead_inbox to service_role;`
   `grant select, insert, update, delete, truncate, references, trigger on public.v_sales_lead_inbox to postgres;`
   Privileges are spelled out explicitly (matching this file's existing style for the `authenticated` revoke line) rather than using `grant all`, so the statement's effect doesn't depend on exactly which relation-level privileges a given Postgres version's `ALL` expands to.
2. Added a "Grants (confirmed live on production via direct query, not inferred)" comment block recording the four-role table above, and explained why all four are made explicit rather than left to ambient behavior: (a) Supabase's schema-level default privileges are known to auto-grant `anon`/`authenticated` on new `public` schema objects — the reason the original migration already revoked/reduced those two — and that hazard applies identically to a freshly `create view`d object; (b) `service_role`/`postgres` ending up with full access again was not independently verified as guaranteed (via default privileges or via migration-runner ownership) rather than assumed, so both are granted explicitly instead of relying on that assumption.

No other SQL changed: the view's column list/order, the RPC body, and `20260828110000_reconcile_sales_is_test_classification.sql` are unchanged from the previous two entries.

No migration was applied, no push, no merge, no deploy. Validation not re-run in this pass (only `.sql` migration files and this status file were touched).
